# Data Layer and Room

## Layer purpose
The data layer stores, retrieves, and transforms app data.
In Aion, that includes tracked apps, app settings, usage sessions, notifications, user profile data, preferences, and future game or shop data.

## Main parts
- Entities: Room table models
- DAOs: database access interfaces
- Database: the Room singleton
- Repositories: app-friendly wrappers around DAOs
- Converters: type conversion helpers for Room

## Entities
Entities are the tables.
The key models are in [data/entities](../../app/src/main/java/com/example/aion/data/entities).

Examples:
- [TrackedAppEntity](../../app/src/main/java/com/example/aion/data/entities/CoreEntities.kt)
- [AppSettingsEntity](../../app/src/main/java/com/example/aion/data/entities/CoreEntities.kt)
- [UsageSessionEntity](../../app/src/main/java/com/example/aion/data/entities/CoreEntities.kt)
- [NotificationEntity](../../app/src/main/java/com/example/aion/data/entities/CoreEntities.kt)
- user and future feature entities in the other entity files

## Room annotations
### `@Entity`
Marks a data class as a database table.
In this app, `TrackedAppEntity` becomes the `tracked_apps` table.

### `@PrimaryKey`
Identifies the unique row key.
Some tables use autogenerated IDs.

### `@ForeignKey`
Creates a relationship between tables.
For example, app settings and usage sessions reference tracked apps.
This helps keep related rows linked and can cascade deletes.

### `@Index`
Speeds up lookups and can enforce uniqueness.
This app uses indexes for package names so app lookup stays fast and stable.

### `@Dao`
Marks an interface that contains Room queries and write methods.
DAOs are the bridge between Kotlin code and SQL.

### `@Database`
Declares the Room database class and lists all entities and DAOs.
See [AionDatabase](../../app/src/main/java/com/example/aion/data/AionDatabase.kt).

### `@TypeConverters`
Lets Room store custom types such as enums or complex values.
See [AionConverters](../../app/src/main/java/com/example/aion/data/converters/AionConverters.kt).

## DAO role
DAOs answer questions like:
- Which apps are tracked?
- What are the settings for this package name?
- What usage sessions exist in this date range?
- Which notifications are unread?

The DAO layer keeps SQL out of the UI and mostly out of ViewModels.

## Repository role
Repositories hide DAO details from ViewModels.
Examples:
- [AppRepository](../../app/src/main/java/com/example/aion/data/repository/AppRepository.kt)
- [UsageRepository](../../app/src/main/java/com/example/aion/data/repository/UsageRepository.kt)
- [NotificationRepository](../../app/src/main/java/com/example/aion/data/repository/NotificationRepository.kt)
- [UserRepository](../../app/src/main/java/com/example/aion/data/repository/UserRepository.kt)

A repository gives the app a cleaner API and makes the data source easier to replace later.

## Database structure in this app
[AionDatabase](../../app/src/main/java/com/example/aion/data/AionDatabase.kt) already includes tables for:
- tracked apps
- app settings
- usage sessions
- notifications
- user profile and preferences
- points and achievements
- shop and inventory
- squads and social features

That means the schema is already shaped for future features, not just the current dashboard.

## Design rule
- UI talks to ViewModels.
- ViewModels talk to repositories.
- Repositories talk to DAOs.
- DAOs talk to Room.

Do not skip layers unless there is a strong reason.
